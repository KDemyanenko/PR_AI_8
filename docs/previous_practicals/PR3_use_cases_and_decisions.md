# Use Cases & Decision Points

**Практична робота №3.** Сценарії використання, точки ухвалення рішень та розмежування відповідальності людини й ШІ.

## 0. System context
- **System name:** Інтелектуальна система керування поведінкою NPC у відеогрі.
- **Target users:** гравці (спостерігають поведінку NPC), розробники та QA-тестувальники (налаштовують і перевіряють її); ігровий рушій викликає функції системи.
- **Main value:** NPC реагують на ігрові події, патрулюють, виявляють противника, атакують, відступають, шукають ціль та допомагають союзникам без ручного керування кожною дією.
- **AI component role:** модель оцінює рівень загрози та пріоритет можливих дій, а перевірені правила і навігація обмежують небезпечні чи неможливі рішення.

**Межі системи:** система NPC отримує стан від ігрового рушія та повертає йому команди дій; інтерфейс розробника дає змогу змінювати параметри й переглядати журнали. **Статус:** це проєктний опис, а не звіт про реалізовану та виміряну програму. Усі числові пороги нижче — **умовні проєктні налаштування** для прикладу; їх можна змінювати під час тестування. Людина не підтверджує кожну дію NPC під час гри: контроль здійснюється через попередні налаштування, тестування, журнали та можливість перевизначити правила.

## A. Use Cases

### UC-01: Патрулювати визначену територію
- **Актор → мета → результат:** ігровий рушій → запустити патрулювання NPC → отримувати команди переміщення між контрольними точками.
- **Primary actor:** ігровий рушій (подія появи NPC).
- **Secondary actors:** розробник (задає маршрут), навігаційний сервіс рушія (NavMesh).
- **Trigger:** NPC з'явився у світі або завершив попередню дію.
- **Preconditions:** NPC активний; маршрут патрулювання заданий; навігаційна сітка доступна.
- **Main flow:**
  1. Рушій передає координати NPC і список контрольних точок.
  2. Система перевіряє, чи доступна наступна точка маршруту.
  3. **[DP-01]** Обирає наступну точку або очікування.
  4. Надсилає рушію команду руху до вибраної точки.
  5. Отримує оновлення позиції та відомості про перешкоди.
  6. **[DP-02]** За потреби перебудовує маршрут або зупиняє рух.
  7. Після досягнення точки продовжує патрулювання.
- **Alternative / exception flows:**
  - **A1:** усі контрольні точки тимчасово недоступні → NPC чекає в поточній безпечній позиції.
  - **E1:** навігаційний сервіс не відповідає → зупинити рух, записати збій і повторити перевірку пізніше.
- **Output / outcome:** команди руху/очікування та статус патрулювання для рушія.
- **Constraints (NFR):** цільовий час вибору чергової дії ≤ 100 мс; зміни маршруту фіксуються в журналі.

### UC-02: Виявити гравця та визначити його статус
- **Актор → мета → результат:** гравець → наблизитися до NPC → побачити реакцію NPC на появу цілі.
- **Primary actor:** гравець.
- **Secondary actors:** ігровий рушій (передає координати й видимість), розробник (налаштовує фракції).
- **Trigger:** гравець потрапляє в радіус сприйняття NPC.
- **Preconditions:** NPC активний; дані про позиції, фракції та перешкоди доступні.
- **Main flow:**
  1. Рушій повідомляє NPC координати гравця й поточний стан сцени.
  2. Система обчислює відстань і перевіряє лінію огляду.
  3. **[DP-03]** Визначає, чи бачить NPC гравця.
  4. Якщо гравця видно, отримує дані про фракцію та недавні агресивні дії.
  5. **[DP-04]** Визначає статус: противник, союзник або невизначена/нейтральна ціль.
  6. Передає рушію команду спостерігати, не реагувати або перейти до бойової поведінки.
  7. Записує причину класифікації для перевірки.
- **Alternative / exception flows:**
  - **A1:** гравець за стіною → NPC не запускає атаку лише за відстанню.
  - **E1:** інформація про фракцію відсутня або модель невпевнена → NPC спостерігає, але не атакує.
- **Output / outcome:** статус виявлення, клас цілі й команда реакції NPC.
- **Constraints (NFR):** цільова реакція ≤ 100 мс; рішення про ворожість має мати запис причини (ознаки/правило/оцінка моделі).

### UC-03: Атакувати підтвердженого противника
- **Актор → мета → результат:** ігровий рушій → передати сигнал про противника → отримати допустиму бойову дію NPC.
- **Primary actor:** ігровий рушій (подія «ворог підтверджений»).
- **Secondary actors:** гравець (ціль дії), розробник (задає бойові обмеження).
- **Trigger:** ціль отримала статус «противник» у UC-02 або атакувала NPC.
- **Preconditions:** NPC активний; дані про здоров'я, дистанцію, озброєння і видимість доступні.
- **Main flow:**
  1. Рушій надсилає стан NPC, противника та зброї.
  2. Система перевіряє, чи не заблокована атака правилами гри.
  3. **[DP-05]** Визначає: атакувати зараз чи утриматися/змінити позицію.
  4. Якщо атака можлива, визначає відстань і доступність зброї.
  5. **[DP-06]** Обирає ближню, дальню атаку або зближення.
  6. Передає рушію команду дії з ідентифікатором цілі.
  7. Отримує результат удару і оновлений стан бою.
- **Alternative / exception flows:**
  - **A1:** ціль зникла з поля зору → перейти до пошуку за UC-05.
  - **E1:** немає боєприпасів або дані зброї відсутні → не виконувати дальню атаку, обрати безпечну альтернативу.
- **Output / outcome:** конкретна бойова команда або команда утриматися від атаки.
- **Constraints (NFR):** цільова затримка вибору ≤ 100 мс; заборонена атака союзника; причина відмови від атаки логується.

### UC-04: Відступити у разі небезпеки
- **Актор → мета → результат:** ігровий рушій → повідомити про загрозу NPC → отримати рішення про відступ і маршрут до укриття.
- **Primary actor:** ігровий рушій (зміна здоров'я/рівня загрози).
- **Secondary actors:** гравець (джерело загрози), навігаційний сервіс, розробник (обмеження на втечу).
- **Trigger:** NPC зазнав шкоди або рівень загрози істотно зріс.
- **Preconditions:** NPC активний; є поточний стан здоров'я та положення на карті.
- **Main flow:**
  1. Рушій передає здоров'я NPC, позицію ворога й інформацію про укриття.
  2. Модель/правила оцінюють загрозу й перевіряють обмеження для NPC.
  3. **[DP-07]** Визначають, чи необхідно відступати.
  4. У разі відступу система формує кандидати: укриття, безпечна зона, союзники.
  5. **[DP-08]** Обирає ціль втечі за досяжністю й рівнем ризику.
  6. Навігаційний сервіс будує шлях до вибраної цілі.
  7. **[DP-09]** Перевіряє шлях; за потреби запитує інший (не більш як дві повторні спроби).
  8. Рушій отримує команду переміщення або безпечної зупинки; результат записується в журнал.
- **Alternative / exception flows:**
  - **A1:** правила забороняють босу тікати → NPC шукає укриття на місці або продовжує визначену сценарієм поведінку.
  - **E1:** жодного придатного маршруту немає → NPC не рухається через перешкоду, залишається в доступному укритті та створює запис про збій.
- **Output / outcome:** команда відступу з цільовою точкою або обґрунтована відмова від відступу.
- **Constraints (NFR):** цільовий вибір рішення ≤ 100 мс без урахування анімації; журнал причин і перевірки маршруту обов'язковий.

### UC-05: Знайти гравця після втрати контакту
- **Актор → мета → результат:** ігровий рушій → повідомити про втрату видимості → отримати команди пошуку або повернення до патруля.
- **Primary actor:** ігровий рушій (подія «ціль втрачено»).
- **Secondary actors:** гравець, навігаційний сервіс.
- **Trigger:** NPC перестав бачити раніше виявленого противника.
- **Preconditions:** NPC активний; система зберігає час і місце останнього контакту, якщо вони відомі.
- **Main flow:**
  1. Рушій надсилає сигнал про втрату прямої видимості.
  2. Система отримує останню відому позицію та час контакту.
  3. **[DP-10]** Обирає: розпочати пошук чи повернутися до патрулювання.
  4. Якщо пошук дозволений, NPC іде до останньої відомої позиції.
  5. Система перевіряє поточну видимість і час від початку пошуку.
  6. **[DP-11]** Вирішує, продовжувати пошук чи завершити його.
  7. Передає команду пошуку, переслідування нововиявленої цілі або патрулювання.
- **Alternative / exception flows:**
  - **A1:** гравця знову видно → повернутися до UC-02 для актуального визначення статусу.
  - **E1:** немає останньої позиції або час події некоректний → не шукати навмання; повернутися до UC-01.
- **Output / outcome:** команда перевірити позицію, продовжити пошук або патрулювати.
- **Constraints (NFR):** часові позначки мають бути монотонними; пошук не повинен бути нескінченним.

### UC-06: Використати ігровий об'єкт
- **Актор → мета → результат:** ігровий рушій → повідомити про доступний об'єкт → отримати допустиму команду взаємодії NPC.
- **Primary actor:** ігровий рушій (NPC наблизився до об'єкта).
- **Secondary actors:** розробник (задає дозволені взаємодії), ігровий світ (стан об'єкта).
- **Trigger:** NPC досяг об'єкта, з яким потенційно може взаємодіяти (двері, важіль, укриття).
- **Preconditions:** об'єкт має ідентифікатор і стан доступності; NPC не виконує несумісну дію.
- **Main flow:**
  1. Рушій передає тип об'єкта, його стан і координати NPC.
  2. Система перевіряє дозволи NPC на взаємодію з цим типом об'єкта.
  3. Обчислює відстань і перевіряє стан блокування.
  4. **[DP-12]** Вирішує: виконати взаємодію чи пропустити об'єкт.
  5. За дозволу передає рушію команду «використати об'єкт».
  6. Записує результат або причину відмови.
- **Alternative / exception flows:**
  - **A1:** об'єкт уже використаний іншою сутністю → пропустити його.
  - **E1:** стан об'єкта невідомий → взаємодію заборонити до оновлення даних.
- **Output / outcome:** команда взаємодії або відмова з причиною.
- **Constraints (NFR):** не надсилати команду для заблокованого об'єкта; фіксувати відмови.

### UC-07: Допомогти союзнику
- **Актор → мета → результат:** союзний NPC через ігровий рушій → запросити допомогу → отримати підкріплення або повідомлення, що допомога недоступна.
- **Primary actor:** союзний NPC (сигнал допомоги через рушій).
- **Secondary actors:** ігровий рушій, розробник (правила командної взаємодії).
- **Trigger:** союзник надсилає подію «потрібна допомога».
- **Preconditions:** союзник і адресат активні; належність до команди та координати відомі.
- **Main flow:**
  1. Рушій передає ідентифікатор союзника, позицію та час запиту.
  2. Система перевіряє команду NPC і актуальність запиту.
  3. Отримує здоров'я адресата, дистанцію до союзника та поточне завдання.
  4. **[DP-13]** Вирішує, чи перервати поточне завдання заради допомоги.
  5. Якщо допомогу дозволено, формує команду руху до союзника.
  6. Рушій повідомляє про прибуття або неможливість руху.
  7. Система записує результат запиту.
- **Alternative / exception flows:**
  - **A1:** адресат виконує обов'язкове сюжетне завдання → зберігає поточну дію.
  - **E1:** позиція союзника відсутня або запит застарів → відхилити запит і залогувати причину.
- **Output / outcome:** команда допомоги/руху або статус відмови.
- **Constraints (NFR):** сигнал допомоги не повинен відволікати NPC із критичних сюжетних станів; обробка журналюється.

### UC-08: Затвердити налаштування поведінки NPC
- **Актор → мета → результат:** розробник → змінити правила поведінки → отримати перевірену та затверджену версію конфігурації.
- **Primary actor:** розробник гри.
- **Secondary actors:** QA-тестувальник, тестовий ігровий рушій.
- **Trigger:** розробник пропонує нові пороги загрози, швидкості реакції або дозволених дій.
- **Preconditions:** розробник авторизований; поточна версія параметрів збережена.
- **Main flow:**
  1. Розробник відкриває редактор параметрів NPC.
  2. Змінює налаштування та зберігає чернетку.
  3. Тестовий рушій запускає контрольні сценарії атаки, втечі й навігації.
  4. Система показує результати тестів, розбіжності та журнали.
  5. **[DP-14]** Розробник вирішує: затвердити версію або повернути на виправлення.
  6. Після затвердження система публікує конфігурацію для наступного запуску гри.
  7. Записує автора, версію, дату й результат перевірок.
- **Alternative / exception flows:**
  - **A1:** критичний тест не пройдено → кнопка публікації заблокована; конфігурацію повернути на доопрацювання.
  - **E1:** виникла помилка під час публікації → залишити чинну версію та повідомити розробника.
- **Output / outcome:** опублікована конфігурація або звіт про причини відхилення.
- **Constraints (NFR):** обов'язковий аудит змін; публікація лише авторизованим розробником після успішних критичних тестів.

## B. Decision Points (table)

> **Умовні правила проєкту:** HP — здоров'я NPC у %; `threat_score` — оцінка загрози від 0 до 1; `confidence` — впевненість моделі від 0 до 1. Пороги, дистанції та час наведено для демонстрації логіки, вони **не є результатами вимірювання або навчання**. **Вартість помилки** стосується якості ігрового процесу та коректності гри, а не реальної фізичної безпеки.

| DP-07 | UC-04 | Чи потрібно NPC відступати? | A: відступити; B: залишитися/сховатися | HP, `threat_score`, тип NPC, правила сюжету | Hybrid (правила + ML model) | якщо втеча дозволена і (HP ≤ 25% або score ≥ 0.85) → A; інакше B | Середня: NPC може загинути або тікати без причини | якщо модель недоступна — HP ≤ 25%; за заборони втечі → B | HP, score, заборона втечі, рішення |

| DP-09 | UC-04 | Чи можна виконати побудований маршрут втечі? | A: рухатися; B: перерахувати; C: зупинитися | статус маршруту, перешкоди, небезпечні зони, кількість спроб | Rule-based | повний і допустимий шлях → A; інакше B не більш як 2 рази, потім C | Висока: NPC може застрягти або пройти крізь об'єкти | C: безпечна зупинка, сигнал у журнал | маршрут, перевірки, кількість повторів |

| DP-11 | UC-05 | Чи продовжувати пошук? | A: продовжити; B: завершити; C: відновити переслідування | час від останнього контакту, видимість, доступні точки пошуку | Rule-based | знову бачить ворога → C; якщо ≤ 10 с і є точки → A; інакше B | Середня: нескінченне переслідування погіршить гру | B за відсутності часу/точок | таймер, видимість, рішення |

## C. Human-in-the-loop matrix

**Розподіл відповідальності:** під час гри рішення NPC автоматичні; розробник/QA втручаються **поза ігровим циклом** через редактор правил, панель діагностики й тести. «Human required when» означає умову **обов'язкової перевірки або підтвердження**, а не миттєве погодження кожної дії NPC.

| DP-ID | AI role | Human role | Human required when | UX form |
|---|---|---|---|---|
| DP-01 | decide (правила) | monitor / override | у QA NPC не може продовжити маршрут після 3 спроб | панель маршруту, кнопка «Змінити точки» |
| DP-02 | detect anomaly / decide (правила) | monitor / override | у QA повторне застрягання в тій самій зоні ≥ 3 рази | попередження та журнал блокувань |
| DP-03 | detect anomaly (перевірка видимості) | monitor / label | QA виявив помилкову видимість або 3 суперечливі події поспіль | візуалізація лінії огляду, позначка тестувальника |
| DP-04 | recommend / decide (ML + правила) | monitor / override / label | модель має confidence < 0.65 у тесті або QA фіксує помилкову атаку союзника | картка рішення з score і причинами, редагування фракції |
| DP-05 | decide (правила) | monitor / override | у тесті атаковано союзника або порушено блокувальне правило | журнал атаки, налаштування заборон |
| DP-06 | decide (правила) | monitor / override | QA повторно бачить вибір недоступної зброї | панель бойових дій і боєприпасів |
| DP-07 | recommend / decide (ML + правила) | monitor / override | під час QA бос утік попри заборону або модель систематично помиляється | перемикач «Втеча дозволена», журнал загроз |
| DP-08 | recommend (оцінка ризику) / decide | monitor / override | у тесті обрано ціль, небезпечнішу за всі доступні альтернативи | карта кандидатних укриттів, оцінки ризику |
| DP-09 | detect anomaly / decide (правила) | monitor / escalate | перевищено 2 спроби перерахунку; повторюється збій маршруту в QA | повідомлення про недоступний шлях, журнал NavMesh |

| DP-11 | decide (правила) | monitor / override | QA фіксує нескінченний пошук або передчасне завершення | журнал таймера, регулятор тривалості пошуку |
| DP-12 | decide (правила) | monitor / override | у тесті NPC відкрив заборонений об'єкт | журнал взаємодій, список дозволів |
| DP-13 | decide (правила) | monitor / override | QA виявив переривання критичної місії через запит допомоги | журнал запитів, редактор пріоритетів |

## D. Flow mapping

### Flow for UC-04: Відступити у разі небезпеки
1. Рушій надсилає здоров'я NPC, відомості про противника та навколишню карту.
2. Система визначає оцінку загрози; перевіряє сюжетну заборону втечі.
3. **[DP-07] Чи відступати?** Якщо **ні** — зайняти укриття/залишитися; якщо **так** — перейти до кроку 4.
4. Система збирає досяжні кандидати (укриття, безпечна зона, союзники).
5. **[DP-08] Куди відступати?** Обрати найменш ризиковану досяжну ціль; якщо кандидатів немає — зупинитися в безпечній позиції.
6. Навігаційний сервіс будує маршрут.
7. **[DP-09] Чи придатний маршрут?** Так → крок 8; ні → повторити побудову до двох разів, потім зупинитися.
8. Передати рушію команду переміщення; записати рішення та його причини.

### Flow for UC-02 → UC-03: Виявлення та реакція
1. Гравець входить у радіус сприйняття NPC.
2. **[DP-03]** Перевірка прямої видимості: ні → зберегти поточну дію; так → крок 3.
3. **[DP-04]** Класифікація цілі: союзник → не атакувати; невизначено → спостерігати; противник → крок 4.
4. **[DP-05]** Перевірка дозволу на атаку: ні → змінити позицію/утриматися; так → крок 5.
5. **[DP-06]** Вибір бойової дії: ближня / дальня атака / зближення.
6. Передати команду рушію й записати вибір та перевірені умови.

**Послідовність обробки:** ігрова подія → вхідні дані → decision point → перевірка правил та можливий fallback → команда рушію → журнал для QA/розробника.

**Окрема схема Mermaid:** файл `npc_use_case_flow.mmd` містить схему сценарію UC-04 з прив'язкою до DP-07, DP-08 і DP-09. Його код можна вставити на сайт Mermaid Live Editor.
